## 2. 耦合控制：三条接缝

全组只要守住三条接缝，其余部分互不阻塞：

```
          ┌──────────── 接缝 1：OpenAPI 契约（schemas/ 由 C 独占）────────────┐
          ▼                                                                 ▼
   A（选课核心）◄── 契约回归测试 ──► C（其余路由）                    D/E（前端，从 OpenAPI 生成 TS 类型）
          │
          ▼
   接缝 2：数据库（sql/ 由 B 独占）── A 只写 SQLAlchemy 查询、不改 DDL
   接缝 3：dev 接口（/dev/strategy 切换 V0–V3，B 的压测脚本依赖，A 提供）
```

- **接缝 1**：C 在第 1 周周二前交付全部 `schemas/` + OpenAPI 快照，之后任何人要加字段先改文档（04 文档流程）。
- **接缝 2**：A 需要新索引先找 B 提 issue，不并发改 `01_schema.sql`；B 的迁移顺序保证 main 永远可起。
- **接缝 3**：`/dev/*` 接口是压测与业务之间的唯一开关，A 保证语义稳定（只切换实现，不改响应体）。
- 另加一条硬规则：**前端只能通过 `src/api/` 访问后端**，任何页面不得内联 URL。

## 4. 结对与 Review

- 每个 PR 至少 1 人 approve，reviewer ≠ author；
- A 的 PR 由 **B** review（两人互审锁逻辑，是质量核心）；
- C 的契约类 PR 由 **D** review（前端验证字段够用）；
- D 的 PR 由 **E** review；E 的 PR 由 **D** 或 **C** review；
- Review 必查四项：锁顺序（先 sections 后 enrollments）、计数与记录同事务、错误码与 02 文档一致、并发相关改动带测试。
