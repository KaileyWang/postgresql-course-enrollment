## 1. 项目概述

### 1.1 背景与目标

教务选课在开放瞬间会形成典型的"读多写极热"混合负载：全量学生短时间内集中访问少量热门课程容量，同时要保证三条硬约束不被破坏——

1. **不超卖**：`enrolled_count <= capacity` 在任何时刻成立，并发下也不例外；
2. **不重复**：同一学生对同一课程同时最多一条有效选课记录；
3. **不冲突**：同一学生的已选课程之间上课时间不能重叠。

本项目的重点不在功能堆砌，而在于**用 PostgreSQL 的并发控制原语（行锁、乐观锁版本号、隔离级别）系统性地解决上述三条约束**，并用可复现的压测数据量化每种方案的取舍。所有实验设计、代码与数据都要求可复现。

### 1.2 你为什么要关心（卖点总结）

| 卖点 | 对应章节 | 答辩时的一句话 |
|---|---|---|
| 防超卖四种方案的对比实验 | 第 7 章 | "同一把压测脚本，只换锁策略，QPS 和错误率差 3 倍以上" |
| 三种隔离级别下的行为差异 | 第 8 章 | "REPEATABLE READ 只会报 40001，不会脏写" |
| 候选队列的原子晋升 | 7.5 | "退课和晋升在同一个行锁窗口内完成，不存在两个学生抢同一个坑" |
| 索引优化的 EXPLAIN 前后对比 | 9.3 | "一个组合索引让课表查询从 12ms 到 0.4ms" |
| 独立压测服务 + 可复现报告 | 第 9 章 | "压测脚本和数据表都在仓库里，任何人可以重跑" |

### 1.3 名词约定

- **教学班（section）**：课程（course）在某学期开设的一个可选的班，拥有独立容量。学生选的是教学班，不是课程。
- **坑位**：`sections.enrolled_count` 计的是"占坑人数"，与状态为 `ACTIVE` 的选课记录数严格一致。
- **V0 ~ V3**：四种防超卖实现方案（见第 7 章），同一套接口，不同内部实现，通过配置切换。
- **降级**：选课失败但进入候选队列（`WAITLISTED`），HTTP 上表现为 202。

### 3.2 技术选型与理由

| 层 | 选择 | 理由 |
|---|---|---|
| 后端框架 | FastAPI + SQLAlchemy 2.0 (async) + asyncpg | 课程要求 Python 栈；async 下连接池行为本身就是报告素材 |

| 前端 | Vue 3 + Vite + Element Plus + Pinia | 组件库现成，表格/弹窗类教务界面直接可用 |
| 压测 | k6 | 脚本化、CI 可跑、输出结构化 JSON，报告好做图 |

## 4. 数据库设计

### 4.1 ER 关系

```
users 1───N enrollments N───1 sections N───1 courses
users 1───N waitlist_entries N──1 sections
sections 1───N section_meetings（上课时间，供给冲突检测）
enrollments N───1 audit（通过 audit_log 记录动作历史）
```

### 4.2 核心表说明

完整 DDL 见 `sql/01_schema.sql`，这里只讲每个设计的"为什么"。

**users**：`student_no` 唯一；`role` 用 ENUM 约束为 `student/admin`。密码存 bcrypt 哈希。测试学生由种子脚本批量插入（学号 `S0001` 起）。

**courses**：课程元信息（编号、名称、学分、院系）。`archived` 软删除标记，避免删课程时级联删历史选课。

**sections**：核心中的核心。除容量 `capacity` 与计数 `enrolled_count` 外：

```sql
enrolled_count INT NOT NULL DEFAULT 0
    CHECK (enrolled_count >= 0 AND enrolled_count <= capacity),
version        INT NOT NULL DEFAULT 0
```

- **CHECK 约束是最后一道防线**：即使应用层出 bug，超卖写入也会被数据库拒绝（V0 实验里我们专门演示它如何行为异常，见 8.4）。
- `version` 服务于 V2 乐观锁。

**section_meetings**：一个教学班可有多段上课时间（如周一 1-2 节、周三 3-4 节）。字段 `weekday`（1–7）、`start_period`/`end_period`（节次，可与前端映射为具体时间）。冲突检测只需比较这两个区间。

**enrollments**：状态机 `ACTIVE → DROPPED`（软退课，保留记录）。关键约束：

```sql
CREATE UNIQUE INDEX uq_enrollments_active
    ON enrollments (student_id, section_id)
    WHERE status = 'ACTIVE';
```

**部分唯一索引**保证"同一学生对同一教学班最多一条有效记录"，且允许退课后重新选（旧记录状态为 DROPPED 不参与唯一性）。这是比应用层查重更可靠的防线。

**waitlist_entries**：`position` 为队列序位。约束 `UNIQUE (section_id, position)`。晋升逻辑见 7.5。

**audit_log**：`action` ∈ `ENROLL/DROP/PROMOTE/DROP_WAITLIST`，记录 `actor_id`、`section_id`、`before/after` JSONB。压测后对账用。

### 4.3 索引设计

| 索引 | 表 | 服务的查询 |
|---|---|---|
| `PK (id)` | 全部 | 主键回查 |
| `uq_users_student_no` | users | 登录 |
| `uq_sections_course_term` | sections | 课程+学期唯一性 |
| `idx_sections_term_dept` | sections | 列表页默认过滤（学期+院系） |
| `idx_sections_term_hot` | sections | 热门榜（`enrolled_count DESC`，部分索引只含开放批次内的班） |
| `uq_enrollments_active` | enrollments | 防重 + 我的课程（`student_id` 前缀） |
| `idx_enrollments_section_status` | enrollments | 班级名单、晋升扫描 |
| `idx_meetings_weekday` | section_meetings | 冲突检测候选集 |
| `idx_audit_section_time` | audit_log | 审计按班+时间回查 |

> 索引不是一次设计完的。第 9.3 节要做"加索引前后 EXPLAIN 对比"，因此基线 migration 故意**不建** `idx_sections_term_dept` 和 `idx_enrollments_section_status`，由索引优化任务单独加。（答辩时这是一个可讲的故事：慢查询从哪来、组合索引列顺序为什么这样定。）

### 4.4 关键约束汇总

| 约束 | 位置 | 防什么 |
|---|---|---|
| `CHECK (enrolled_count BETWEEN 0 AND capacity)` | sections | 任何路径下的超卖/负计数 |
| 部分唯一索引 `uq_enrollments_active` | enrollments | 重复选课 |
| `UNIQUE (section_id, position)` | waitlist_entries | 队列位置重复导致晋升混乱 |
| `FOREIGN KEY ... ON DELETE RESTRICT` | enrollments→sections | 误删有选课记录的教学班 |
| 应用层：时间区间冲突 | services/conflict.py | 课表冲突（不能用约束表达） |

### 4.5 选课阶段的"开/关"

`sections` 通过 `selection_term_opened` 与全局开关实现：写入阶段之外，选课接口统一 423。全局开关存 `system_config` 表（`key='selection_open'`），管理员可改。压测脚本会先调 `POST /api/v1/dev/selection/open` 打开写阶段。

## 6. 并发控制总纲

我们的场景可以抽象成一句话：**几千个写事务争抢同一行（教学班）上的一个计数，同时每个写事务还要读自己名下的其他行做冲突判断。**

围绕这句话建立纪律：

1. **热点在何处**：`sections` 的单个行是唯一写热点。所有方案都必须在这行上串行化（或原子化）一次。
2. **读一致性**：冲突检测读的是学生自己的课程集合，跨行。用隔离级别控制"读得准不准"。
3. **约束的层次**：应用层锁只是为了控制**错误形态**（409 还是 202 还是重试）；正确性最终由数据库约束兜底（CHECK、部分唯一索引）。

一句话选型结论（详细实验见第 7、8 章）：**生产实现用 V3（原子条件更新）；教学与对比实验保留 V0–V2。**

## 7. 防超卖四方案（V0–V3）详细设计

四个方案共享同一个策略接口：

```python
# services/enrollment/strategy.py
class EnrollmentStrategy(Protocol):
    async def enroll(self, session, student_id: int, section_id: int,
                     allow_waitlist: bool) -> EnrollmentResult: ...
```

工厂按 `settings.enrollment_strategy` 返回实例。所有方案都必须通过同一组并发正确性测试（`tests/integration/test_concurrency.py`：50 个协程抢 3 个坑，断言成功数恰好为 3，且 `active` 记录数 = 3）。

### 7.1 V0：朴素实现（对照组，故意有竞态）

```python
async def enroll(session, student_id, section_id, allow_waitlist):
    section = await session.get(Section, section_id)
    if section.enrolled_count >= section.capacity:      # ← 读到 3，容量 4
        return WAITLIST_OR_FULL
    # 两个请求都通过了上面的判断……
    await session.execute(text(
        "INSERT INTO enrollments (student_id, section_id, status) VALUES (:s, :c, 'ACTIVE')"
    ), {"s": student_id, "c": section_id})
    await session.execute(text(
        "UPDATE sections SET enrolled_count = enrolled_count + 1 WHERE id = :c"
    ), {"c": section_id})
    return ENROLLED
```

行为要点：计数检查与 `UPDATE` 是两个独立语句，`UPDATE` 不读旧值，因此**不会抛任何锁错误**；超卖发生在应用层判断窗口内。`UPDATE` 本身原子，所以计数仍等于插入成功的行数（没有"计数虚高"），但会超过容量——正是"应用逻辑没锁住"的经典形态。若把 `UPDATE` 写成 `SET enrolled_count = :old + 1`（回填路径），还会出现**丢失更新**，计数小于实际行数；两种错误形态都写进实验报告。

### 7.2 V1：悲观锁（SELECT … FOR UPDATE）

```sql
BEGIN;
SELECT id, capacity, enrolled_count FROM sections
 WHERE id = :section_id FOR UPDATE;          -- 行锁，后继者排队
-- 应用层：判断容量 → 冲突检测 → INSERT → UPDATE count
COMMIT;
```

- 正确性：同一时刻只有一个事务持有该行的锁，判断+修改原子，杜绝超卖。
- 错误形态：并发下后继事务**阻塞等待**（lock wait），高并发时 P99 上升，极端下出现 `lock_timeout`。
- 死锁风险：两个选课事务若按相反顺序获取多把行锁（例如同时锁 sections 和 users 的行做余额检查），可能死锁。**纪律：全局锁顺序 = 先 sections、后 enrollments，任何路径不得颠倒。**（代码评审检查项。）

### 7.3 V2：乐观锁（version 版本号）

```sql
BEGIN;
SELECT version, capacity, enrolled_count FROM sections WHERE id = :section_id;
-- 应用层判断容量、冲突检测
UPDATE sections SET enrolled_count = enrolled_count + 1, version = version + 1
 WHERE id = :section_id AND version = :v AND enrolled_count < capacity;
-- rowcount = 0 → 冲突或已满 → ROLLBACK，按退避策略重试（上限 3 次）
COMMIT;
```

- 正确性：`WHERE version = :v` 是 CAS，只有一个事务能成功提交，其余 rowcount=0 后重试。
- 错误形态：**重试风暴**。热点行上重试概率接近 1——第 N 个并发请求平均要 3 次才能成功；超过重试上限返回 409 "请稍后重试"。这恰恰是报告里最有说服力的数据（见 9.2 实验表）。
- 适用性：读多写少的行（如课程详情更新）非常适合；热点选课场景是**反面教材**。

### 7.4 V3：原子条件更新（生产方案）

```sql
BEGIN;
UPDATE sections
   SET enrolled_count = enrolled_count + 1, version = version + 1
 WHERE id = :section_id AND enrolled_count < capacity;
-- rowcount = 0 → 已满（或不存在）→ 不再重试，直接走候选/返回满
-- rowcount = 1 → INSERT enrollment，任何失败整体 ROLLBACK
COMMIT;
```

- 正确性：单条 `UPDATE` 上的行锁 + 条件重估。PostgreSQL 在 `UPDATE` 获取行锁后重新评估 `WHERE`，因此"条件为真时的读"和"写"发生在同一临界区，不存在判断窗口。
- 错误形态：已满时 rowcount=0 是**确定性结果**，不是错误——直接转入候选队列逻辑（7.5），不产生重试。
- 与 V1 的区别：V1 先在应用层拿锁再判断（持锁跨越多次往返），V3 把判断下沉进一条语句（持锁窗口最短）。
- 一条 SQL 会不会漏掉唯一约束错误？会——`INSERT` 若触发 `uq_enrollments_active`（重复选课），整个事务回滚，计数自愈。这依赖"计数与记录同事务"纪律。

### 7.5 候选队列与原子晋升

数据流：满员 → 若 `allow_waitlist=true`，插入 `waitlist_entries(status='WAITING', position=max+1)` 返回 202 + 排位；否则 409。

退课路径（`DELETE /enrollments/:id` 或管理员删课触发）必须在**同一个事务、同一个行锁窗口**内完成"减坑 + 晋升"：

```python
async def drop_and_promote(session, enrollment_id):
    async with session.begin():
        row = await session.execute(text("""
            SELECT e.section_id FROM enrollments e
             WHERE e.id = :eid AND e.status = 'ACTIVE' FOR UPDATE
        """), {"eid": enrollment_id})
        section_id = row.scalar_one_or_none()
        if section_id is None:
            return NOT_FOUND
        await session.execute(text("""
            UPDATE enrollments SET status = 'DROPPED', dropped_at = now() WHERE id = :eid
        """), {"eid": enrollment_id})
        await session.execute(text("""
            UPDATE sections SET enrolled_count = enrolled_count - 1, version = version + 1
             WHERE id = :c
        """), {"c": section_id})
        w = await session.execute(text("""
            SELECT id, student_id FROM waitlist_entries
             WHERE section_id = :c AND status = 'WAITING'
             ORDER BY position LIMIT 1 FOR UPDATE SKIP LOCKED
        """), {"c": section_id})
        ...  # 晋升：改变 enrollment 为 ACTIVE 或新建，更新 waitlist 状态，enrolled_count + 1
```

关键点：

1. **减坑和晋升必须同事务**：否则出现"坑已减、晋升失败"或"两个事务各减坑各晋升"的双重错误。若晋升失败（如候选者此时与其他课程冲突），整体回滚，坑位回到原位、候选人仍在队首——等待下一次退课。
2. **`FOR UPDATE SKIP LOCKED`** 取队首：多个并发退课不会有等待；被锁住的队首临时跳过（实践中该锁只持续一个短事务）。
3. **idempotency**：退课重复提交，第二次因 `status='ACTIVE'` 条件不满足（`FOR UPDATE` 拿到的是 DROPPED 行，返回 404），天然幂等。

### 7.6 冲突检测算法

```python
# services/conflict.py
def conflicts(new_meetings, chosen_meetings) -> list[Meeting]:
    """区间重叠：同一 weekday 且 [start1,end1] ∩ [start2,end2] ≠ ∅"""
    out = []
    for m in chosen_meetings:
        for n in new_meetings:
            if m["weekday"] == n["weekday"] and \
               n["start_period"] <= m["end_period"] and \
               m["start_period"] <= n["end_period"]:
                out.append(n)
    return out
```

执行时机：**放在拿锁之后**（V1/V3 的事务内）。若放在锁外先读，候选集可能过期——读到的是快照，判断完再写时学生可能刚选了另一门课。纪律：冲突检测读的是事务内快照，且事务内已锁定目标 section 行，杜绝"检测过期"。

区间重叠的 SQL 版本（供可选优化）：

```sql
SELECT 1 FROM section_meetings m1
 JOIN enrollments e ON e.section_id = m1.section_id AND e.student_id = :sid AND e.status='ACTIVE'
 JOIN section_meetings m2 ON m2.section_id = :target_section
 WHERE m1.weekday = m2.weekday
   AND m1.start_period <= m2.end_period
   AND m2.start_period <= m1.end_period
LIMIT 1;
```

### 7.7 四种方案对比总结

| | V0 朴素 | V1 行锁 | V2 乐观锁 | V3 原子更新 |
|---|---|---|---|---|
| 正确性（不超卖） | ❌ | ✅ | ✅ | ✅ |
| 高并发错误形态 | 静默超卖 | 锁等待、P99 抖 | 409 重试风暴 | 满员即 202/409，确定 |
| 锁持有窗口 | — | 长（应用往返内） | 短（仅 CAS） | 最短（单语句） |
| 可重试性 | — | 可（有界） | 必须重试，热点下概率近 1 | 无需重试 |
| 实现复杂度 | 低 | 中 | 中高 | 低 |
| 结论 | 对照组 | 教学演示 | 反例 | 生产 |

## 8. 隔离级别实验（核心报告章节）

### 8.1 为什么要做这一章

选课系统给了一个绝佳的课堂：同一批并发事务，只改 `isolation_level`，就能观察到"阻塞"与"中止"两种完全不同的系统形态。这一章回答三个问题：(a) 默认隔离级别是什么行为；(b) 更高隔离级别换来了什么、又付出了什么；(c) 应用层需要配合什么（重试）。

### 8.2 默认级别：READ COMMITTED

PostgreSQL 默认 `READ COMMITTED`。每个语句看到的是语句启动时的已提交快照，语句执行中会重新评估：

- V1 下，`SELECT ... FOR UPDATE` 排队到锁释放后，**会读到最新已提交版本**（行被重新检查，如被删除则可见性判断更新）。这就是 V1 正确性的来源。
- V3 下，`UPDATE` 在行锁上重评估 `WHERE`，即使快照里计数旧，条件仍被正确维护。
- 风险点：**应用层多语句读**（先读名额、再写）在 RC 下不是原子的——这正是 V0 的错误根源，也是 RC 下绝不能用"读后写"模式的证据。

### 8.3 REPEATABLE READ

每个事务使用事务级快照。在 PG 中 RR 也**防止丢失更新**（因写冲突抛错而非覆盖）：

- 两个事务同时改同一 section 行：后提交者收到 `ERROR: could not serialize access due to concurrent update`（SQLSTATE 40001）。**不会静默覆盖**。
- 对 V3 的影响：RR 下热点行竞争从"行锁排队"变为"排队 + 40001 报错"，**成功率下降**。这解释了为什么生产选课系统更倾向 RC + 原子语句（或应用层重试）。
- 实验设计：同一压测脚本，`isolation_level=REPEATABLE_READ` 时统计 40001 出现次数与成功 QPS。预期：成功 QPS 不升反降，错误码集中在 40001（V2/V3 均需全局重试装饰器）。

### 8.4 SERIALIZABLE

SSI（可串行化快照隔离）在 RR 基础上检测读-写依赖环，在**可能产生不可串行化结果时主动中止**事务（40001）。对选课系统：

- 收益：任何"先读后写"的错误模式都会被系统拒绝，V0 那种朴素实现也会被 40001 兜住。
- 代价：热点行上冲突率极高，与 RR 一样需要应用层重试整个事务；并且 SELECT 不再是免费的（SSI 需要跟踪谓词读）。
- 实验设计：V3 代码不变，仅切换 `SERIALIZABLE`，观察 V0 的错误从"静默超卖"变为"报错中止"——这是报告里最有说服力的一张图：**同一段错误代码，在 SERIALIZABLE 下不再产生错误数据，而是转为可重试错误**。这说明"隔离级别是一种防御性编程"。

### 8.5 实验矩阵

| 组合 | 预期现象 | 采集数据 |
|---|---|---|
| V0 × RC | 超卖（计数 < 实际成功记录数或计数超过容量，取决于写法） | 超卖数、对账差异 |
| V0 × RR | 部分请求 40001；不产生超卖 | 40001 次数、成功数 |
| V0 × SERIALIZABLE | 全部可能不可串行的组合被拒 | 40001 次数、成功数 |
| V1 × RC | 无超卖；锁等待 | P99、lock wait 时间 |
| V1 × RR | 无超卖；40001 少量出现 | 40001 次数 |
| V2 × RR | 40001 为主 | 重试次数分布 |
| V3 × RC（生产） | 无超卖、无重试 | 基线 QPS |
| V3 × SERIALIZABLE | 无超卖；40001 出现 | 与 RC 差值 |

> 所有测试用同一个 `bench/k6_grab.js`，通过环境变量 `TARGET_SECTION_ID` + `ENROLLMENT_STRATEGY` 控制变量。结果写入 `bench/results/<date>/<strategy>_<isolation>.json`。

### 8.6 对账脚本

压测结束后自动执行（`bench/reconcile.sql`）：

```sql
SELECT s.id,
       s.capacity,
       s.enrolled_count,
       COUNT(e.id) FILTER (WHERE e.status='ACTIVE') AS actual,
       s.enrolled_count - COUNT(e.id) FILTER (WHERE e.status='ACTIVE') AS drift
FROM sections s
LEFT JOIN enrollments e ON e.section_id = s.id
GROUP BY s.id, s.capacity, s.enrolled_count
HAVING s.enrolled_count <> COUNT(e.id) FILTER (WHERE e.status='ACTIVE')
    OR s.enrolled_count > s.capacity;
```

（drift 非空 = 计数与记录不一致；enrolled_count > capacity = 超卖。）
